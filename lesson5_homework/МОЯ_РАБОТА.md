# Сервис уведомлений

Автор: Юров Егор

## Что делает программа

Сервис отправляет учебные уведомления через email и push с помощью общего интерфейса `Notifier`. При успешной отправке сообщение получает префикс с именем канала и сохраняется в его истории `Messages`. Настоящая отправка писем и push-уведомлений не выполняется.

## Как запустить

Команды выполняются из корневой папки репозитория. В `go.mod` указана версия Go 1.27; проверка выполнена на Go 1.27.1.

```bash
cd ./lesson5_homework
go run ./cmd/notify
go test -v ./...
go build ./...
go vet ./...
gofmt -l tasks.go cmd/notify/main.go
```

Логика сервиса находится в пакете `practice`, а демонстрационная программа — в `cmd/notify/main.go`. Команда `go run ./cmd/notify` показывает все четыре случая ниже. Все существующие тесты проходят.

## Проверенные случаи

1. **Успешная отправка.** У email задан `Address`, у push — `DeviceID`. При отправке `Заказ готов` через `Dispatch` возвращается `nil`, а в истории каналов с именами `email` и `push` появляются `[email] Заказ готов` и `[push] Заказ готов`.
2. **Пустой текст.** При отправке `""` через `Dispatch` первый канал возвращает `ErrEmptyMessage`, а диспетчер оборачивает ошибку с помощью `%w`. Проверка `errors.Is(err, ErrEmptyMessage)` возвращает `true`. Истории не меняются. Даже если настройка тоже отсутствует, первой возвращается ошибка пустого сообщения.
3. **Нет настройки.** Push с именем `push`, без `DeviceID` и с непустым сообщением возвращает `*SendError`. Через `errors.As` можно получить `Channel: "push"` и `Reason: "не задан device id"`. Строка этой ошибки — `канал push: не задан device id`; история остаётся прежней. Для email без адреса причина — `не задан адрес`.
4. **Паника одного канала.** В `SafeDispatch` сначала передаётся `BrokenNotifier`, затем исправный push, а текст сообщения — `Заказ готов`. Паника первого канала преобразуется в ошибку, распознаваемую через `errors.Is(err, ErrNotifierPanic)`. Диспетчер продолжает работу: следующий канал получает сообщение, и в его истории появляется `[push] Заказ готов`. Возвращается список из одной ошибки.

## Обработка ошибок

`Dispatch` вызывает `Send` по очереди и останавливается на первой ошибке. Он добавляет имя канала через `fmt.Errorf` с `%w`, сохраняя исходную причину. Уже выполненные отправки не отменяются. Панику этот диспетчер не перехватывает.

`SafeDispatch` вызывает каждый канал через `SafeSend`, продолжает работу после ошибок и возвращает срез всех собранных ошибок. `SafeSend` возвращает обычную ошибку без замены, а панику преобразует в ошибку с причиной `ErrNotifierPanic`.

`errors.Is` используется для проверки известных ошибок `ErrEmptyMessage` и `ErrNotifierPanic`, в том числе через обёртки. `errors.As` извлекает типизированную ошибку настройки `*SendError`; читать её поля можно только после успешной проверки:

```go
if errors.Is(err, ErrEmptyMessage) {
    fmt.Println("Нельзя отправить пустое сообщение")
}
if errors.Is(err, ErrNotifierPanic) {
    fmt.Println("Канал завершился с паникой")
}

var sendErr *SendError
if errors.As(err, &sendErr) {
    fmt.Println(sendErr.Channel, sendErr.Reason)
}
```

Такие проверки используются в тестах и в `main` файла `cmd/notify/main.go`, где программа выбирает, что вывести пользователю. Для результата `SafeDispatch` в цикле проверяется каждая ошибка из среза. Сами каналы и диспетчеры ошибки в консоль не печатают.

`recover` находится в отложенной функции внутри `SafeSend`, вокруг отдельного вызова `Send`. Поэтому после паники управление возвращается в цикл `SafeDispatch`, который может вызвать следующий канал. Если перехватывать панику только вокруг всего цикла, после восстановления функция завершится и оставшиеся каналы не будут вызваны.
